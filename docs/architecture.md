# Данные и будущий сервер

## Непрерывность

История — упорядоченная последовательность смен состояния. Первая запись всегда «Нет данных» в момент начала даты рождения (локальная полночь при регистрации, сохранённая как UTC timestamp). Конец записи равен началу следующей. Последняя запись продолжается до текущего момента и далее до следующего переключения.

Так промежутки покрыты по построению: интервалы полуоткрытые [начало, конец), без дыр и пересечений. Перед сохранением проверяются начало истории, порядок времени, уникальность ID и допустимые состояния. При переводе часов назад новое переключение блокируется, если его время не позже предыдущего. Подсчёты обрезают интервалы по границам выбранного периода; календарные сутки и недели считаются в текущем часовом поясе устройства.

Будущее удаление записи должно восстанавливать покрытие состоянием «Нет данных» или объединять соседние интервалы. Нельзя просто вырезать время из истории.

## Текущая локальная реализация

Database schemaVersion=1 содержит профили и ID локального сеанса. Каждый профиль имеет стабильный UUID, revision, updatedAt, дату рождения, настройки и события с UUID. SQLite / IndexedDB атомарно читают и записывают актуальный снимок. Пароль хранится как соль, параметры KDF и хеш, исходный пароль не сохраняется. Статистика вычисляется из событий, отдельные счётчики не хранятся.

Хранилище пока сохраняет снимок JSON. Это простой начальный вариант; для больших историй понадобится таблица событий с индексом user_id/at и запросами страниц вместо загрузки всего снимка. UI уже показывает по 20 записей.

## Будущее развёртывание

Предлагаемый вариант: PostgreSQL в Docker на сервере пользователя, постоянный volume и резервное копирование. Мобильное приложение обращается к HTTPS API, а не напрямую к порту БД. Сервер ещё не создан и ничего не развёрнуто.

Repository отделён от экранов: позже вход/регистрацию заменит серверный Auth API, локальный слой останется для офлайн-доступа. Нужно предусмотреть привязку существующего локального UUID к подтверждённому серверному аккаунту и явный импорт локальной истории; совпадение username само по себе не доказывает владение аккаунтом. Локальную соль/хеш нельзя автоматически считать серверной учётной записью.

## Синхронизация — ещё не реализована

Потребуются журнал локальных операций, уникальные operation ID, подтверждения сервера, повторные отправки без дубликатов и серверная ревизия. Наличие UUID и revision сейчас не означает, что слияние уже работает.

Нельзя применять last-write-wins ко всему массиву: это потеряет независимые офлайн-записи. При конфликте двух состояний на одном временном интервале понадобится согласованная политика и, при необходимости, выбор пользователя. После слияния обязательно повторно проверять непрерывность от рождения. Даты устройств нельзя считать достаточным источником причинного порядка. Серверная авторизация, хранение сессий и миграция данных — отдельный этап.
