# Данные и будущий сервер

## Непрерывность

История — упорядоченная последовательность смен состояния. При регистрации первая запись — «Нет данных» в момент начала даты рождения (локальная полночь при регистрации, сохранённая как UTC timestamp). Конец записи равен началу следующей. Последняя запись продолжается до текущего момента и далее до следующего переключения.

Так промежутки покрыты по построению: интервалы полуоткрытые [начало, конец), без дыр и пересечений. Перед сохранением проверяются начало истории, порядок времени, уникальность ID и допустимые состояния. При переводе часов назад новое переключение блокируется, если его время не позже предыдущего. Подсчёты обрезают интервалы по границам выбранного периода; календарные сутки и недели считаются в текущем часовом поясе устройства.

Редактор заменяет удалённые участки на «Нет данных» и объединяет соседние одинаковые состояния. Начало истории всегда совпадает с датой рождения; исходное неизвестное состояние тоже допускает ручное уточнение. Сохранение сверяет ревизию профиля в транзакции. Состояние после момента открытия редактора сохраняется. Полосы до изменений вычисляются относительно снимка на момент открытия.

## Текущая локальная реализация

Database schemaVersion=1 содержит профили и ID локального сеанса. Каждый профиль имеет стабильный UUID, revision, updatedAt, дату рождения, настройки и события с UUID. SQLite / IndexedDB атомарно читают и записывают актуальный снимок. Новые сеансы содержат серверный токен. Хеши старых локальных профилей используются для проверки владения при миграции. Статистика вычисляется из событий, отдельные счётчики не хранятся.

Хранилище пока сохраняет снимок JSON. Это простой начальный вариант; для больших историй понадобится таблица событий с индексом user_id/at и запросами страниц вместо загрузки всего снимка. UI уже показывает по 20 записей.

## Серверный API

Docker Compose запускает PostgreSQL и HTTP API. SQL-миграции создают таблицы профилей, сеансов и событий. Сервер проверяет ревизию перед записью всей истории в транзакции. Конфликт возвращает HTTP 409. Для публикации на сервере нужен HTTPS перед API и резервное копирование тома PostgreSQL. Контракт описан в [инструкции сервера](../backend/README.md).

## Синхронизация

Клиент хранит серверный UUID профиля, токен сеанса и последний согласованный снимок. Изменения сначала записываются в IndexedDB или SQLite. При открытии, восстановлении связи, возвращении в приложение и периодически во время работы клиент сверяет профиль и историю. Локальная ревизия защищает редактор, серверная ревизия защищает запись в PostgreSQL.

На каждой границе времени сравниваются исходное, локальное и серверное состояния. Независимые правки объединяются; при разногласии в одном интервале пользователь выбирает источник спорных значений. Доступ к аккаунту требует серверного входа. При истечении сеанса локальные изменения остаются до повторного входа тем же пользователем.
